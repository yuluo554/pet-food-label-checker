| 3 | 净含量未知单位落 `not_found` | "写了但单位不认识"被混同"根本没写" | 正则只抓"关键词+数值"，单位按**最长优先**已知表判定；认不出 → `mapping_uncertain` |
| 4 | 日期不校验合法性 | `2026-13-45` 被当有效日期 | `datetime.date()` 校验 → 非法记 `out_of_range` 且**丢弃该字段**（不"标个非法还当已提供"） |

**顺带修掉的两处假门**（都是"看起来有处置、实际空转"）：

1. **脱敏审计的死豁免**：给原文快照声明的 `generic_email` 豁免**是死代码**
   （扫描器内联实现、没调 `_is_exempt`），该文件照报 `REVIEW 1`——与文档记的 `REVIEW 0` 不符。
   已接上豁免表并补**双向**非空转自检。**只验豁免函数本身，验不到"扫描器有没有调它"**。
2. **GUI 政策字面量门禁的 `abs<100` 豁免**：M1 只修了**引擎**侧这处勘误（K5），
   **界面侧（AST 断言三）原样留着**——而政策数值天然 <100（实测 0.09–28）→ **整包放过**。
   实测：注入真实限值 `28` 到 `gui/app.py`，门禁**照绿**。已改为"与规则包限值同形即违规"
   （根治判据 + 断言 token 集非空）+ 结构性豁免收紧为"整数且 <20、非整数不豁免"。
   **教训：同一处勘误修了一边，另一边会原样留着。**

### M6 实录：本棒做了什么

**M6 的题眼不是"打个包发出去"，而是"发布这一步能不能被陌生人复核"。**
故本棒把重心放在三条**可核证**上，而不是"上传成功"这个动作本身：

**① 新增发布打包通路**（`tools/make_release.py` + `tests/test_release.py` 21 项 + CI 接线）。
两条口径一起守：**打包确定性**（`ZIP_STORED` + 条目字典序 + 固定时间戳 + 固定外部属性）
与**产物本体脱敏扫描**。后者是必须另立的通路——`dist/` 在 `.gitignore` 内，
`audit_desensitize.py --tracked` **看不到它**（M5 记过这个盲区），而发行包是
**要发给陌生人的东西**，带本机路径的后果最重。

**② 变异验证 10 处**（全部确认变红，且**对照组有效**）。当场抓出自己写的一处假门：
新加的"边界环视"阴性对照用的是 `ASUSTek COMPUTER INC`——它**根本不含**针
`Users\<用户名>`，靠**前缀**就排除了，边界环视整段空转（删掉环视测试仍绿）。
改用 `Users\<user>Other` 这类**真边界**样本后才真的探活。

**③ CI 首跑抓出 3 个真缺陷**（本地源码态全都看不见，详见 `plan/RELEASE-M6.md` §五）：
新门判据张冠李戴（ubuntu runner 上用户名恰好是 `runner`，触发另一条判据的合法命中）、
留档对账要求了做不到的事（PyInstaller 跨次重建不逐字节可复现）、
REVIEW 级误当阻断项（会随 runner 变化时红时绿）。
**这正是"首次上 CI"不可替代的价值**——三个都不是靠本机多跑几遍能发现的。

**另**：转公开三清中做了一次**本地历史重写**（`tools/rewrite_history_m6.py`），
把两处历史里的本机用户名路径与全部提交邮箱清干净（HARD 3→0）。
邮箱改写走 `--email-callback` 而非 `.mailmap`——后者每行都要原样写出旧邮箱，
那文件要么入仓（自曝）要么留工作区（下次 `git add -A` 就带上）。

**M6 末态**：`pytest -q` → **297 passed**（3.8 与 3.12 双解释器）；
`tools/make_release.py --dist dist --out release --check` → **`RELEASE_PACK_OK`**；
两树冻结验收 `VERIFY_FROZEN_OK`；CI **7/7 全绿**（run `38705277036`）；
`docs/DIST-sha256-M6.txt` 与 GitHub 上的附件 sha256 逐条一致。

## 里程碑收尾固定顺序

```
DoD 验证 → plan/00·05·06 状态回写 → 写 HANDOFF-M<next> → commit →（有远端则 push 等 CI 绿）
```

**"HANDOFF 已落盘"与"测试全绿"同属收尾 DoD。**

**M6 是最后一个里程碑**：出口门是 `plan/HANDOFF-FINAL.md`（末态基线 / 发布执行记录 /
复跑手册 / 遗留项），而不是 HANDOFF-M7。发布类收尾的顺序是：

```
三清（历史 / 失败 run / 元数据）→ 建远端（先 private）→ push → 等 CI 首跑绿
  → 打 tag + 建 Release + topics → 真下载复核 → 切 public → 发布后全新 clone 复核
```

**为什么先 private 后 public**：CI 首跑几乎必然暴露环境差异（M6 实测 3 个真缺陷）。
在 private 阶段修完再切 public，公众看到的是绿的；反过来则会把红的 run 留在公开历史里。

**里程碑阻塞在用户动作而非完成时**：更新当前 HANDOFF 待办区 + 续接指针，**不写虚构的 next HANDOFF**（区分"完成收尾"与"中断暂停"两种出口）。

## 每周可演示的验证命令

```bash
# 状态与规则概览
pflc diagnostics

# 单件核验
pflc check data/samples/label-demo-missing.txt

# 基准四套件
pflc bench

# 导出报告
pflc report data/samples/label-demo-ok.txt --out output/

# 冻结态自检（打包后）
pflc.exe --selftest output/selftest.json

# 发布打包 + 三条判据（确定性 / 回读保真 / 产物本体脱敏）
py -X utf8 tools/make_release.py --dist dist --out release --check

# 真下载复核（下载附件 → sha256 对账 → 中立目录解压 → 跑冻结态自检）
gh release download v0.1.0 && sha256sum -c ...   # 对账表见 docs/DIST-sha256-M6.txt
```

## M6 之后的维护注意（留给后来者）

| 事 | 为什么 |
|---|---|
| **改 `src/` 或 `tools/pflc.spec` 后必须重打 Release 产物** | 否则"产物与源码同基线"这条断掉（`git diff <发布基线>..HEAD -- src/ tools/pflc.spec` 不再为空）。发布基线 = `v0.1.0` 指向的提交 |
| **重打产物后必须更新 `docs/DIST-sha256-M6.txt`** | 留档记的是 zip sha256 + 文件数 + **树 sha256**。不更新则 `test_shipped_release_ledger_matches_archives` 会在"同一棵树"时变红（这是预期行为） |
| **`release/` 在 `.gitignore` 内，别 `git add` 它** | 那两个 zip 合计 128 MB，走 Release 附件而不是仓库 |
| **PyInstaller 产物跨次构建不可逐字节复现** | 别用"在别处重建一次"来核对留档哈希——见 `plan/RELEASE-M6.md` §五·② |
| **改脱敏判据要同时看两条通路** | `audit_desensitize.scan_criteria()`（文本）与 `sensitive_literals()`（产物本体）同源，但服务不同场景；改一处要确认另一处仍成立 |
