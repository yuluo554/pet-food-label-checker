> 版本：**M1 数据先行版**（2026-10-15）。规则包已录入并逐条挂原文核对（45 条：43 `verified` / 2 `pending`），

## 一、问题定义

养宠人核验一袋猫犬粮标签，需要同时回答三类问题：

| 问题 | 依据 | 难点 |
|---|---|---|
| 强制标示项是否齐全？ | 《宠物饲料标签规定》 | 条款散在规章正文与附件里，人工逐条对照必然漏项 |
| 保证值是否达标？ | GB/T 31216—2014 / GB/T 31217—2014 | 标准正文不易获得；限值按**生命阶段**分档，需先正确识别档案所属档位 |
| 宣称用语是否有据？ | 《宠物饲料标签规定》限定用语条款 | "天然""无谷"是受约束的限定用语，条件齐备性需结构化核查 |

**现有替代方案的问题**：商业侧"AI 点评配料表"输出一段自然语言，**不可复现**（同一输入两次结论可能不同）、**无条款依据**（无法核证"依据哪一条"）、**无逐项结论**（无法回答"到底哪一项不合格"）。

**本项目的技术主张**：把可机器判定的条款抽成**结构化规则包**，用**确定性引擎**逐项判定，产出**带条款锚点的三态结论**，并用**合成标签基准**证明引擎正确。四条性质是"可验证性"的具体含义：可复现、可溯源、可区分、可证伪。

## 二、规则化方法（法规条款 → 结构化规则）

### 2.1 三层数据组织

```
原文快照（data/knowledge/raw/）        ← 权威原文，-text 冻结，登记 sha256
        ↓ 脚本转写（禁手抄）+ 原文逐字包含断言
条文块（data/knowledge/clauses/*.json） ← 按条款号索引的结构化条文
        ↓ 生成器（tools/gen_rulesets.py）
规则包（data/rules/ruleset-*.json）     ← 冻结产物，禁手改，位级一致守门
```

**为什么必须脚本转写**：手抄数百个数值必然引入不可复现的转写漂移，且无法复核。转录器按**条文号索引**解析（标准正文是 `X.Y → X.Y.N` 编号树，按条文号切块后目标值各落确定条文），**每一处抽取值断言原文逐字包含**——这把"转录对不对"从"人工校对"变成"机器可判定"。

### 2.2 规则条目结构

```json
{
  "rule_id": "NUT-001",
  "dimension": "nutrition",
  "kind": "threshold",
  "target": "粗蛋白",
  "effect": "obligation",
  "op": ">=",
  "value": "26",
  "unit": "%",
  "applies_if": {"category": ["猫粮"], "life_stage": ["成年"]},
  "status": "verified",
  "clause_status": "verified",
  "anchor": {"doc_id": "...", "clause": "...", "source_url": "...", "sha256": "..."}
}
```

三类判定方式（`kind`）覆盖全部需求：

| kind | 语义 | 判定逻辑 |
|---|---|---|
| `presence` | 标示项是否提供 | 已提供 → 符合；无条件义务缺失 → **不符合**；原文写了例外且命中 → 不适用 |
| `threshold` | 保证值 vs 限值 | 按 `applies_if` 筛档 → `Decimal` 比较 → 符合/不符合/未提供 |
| `claim_support` | 宣称条件齐备性 | 宣称存在 → 检查所需信息支撑是否齐备 |

### 2.3 版本化与冻结

规则包是**冻结产物**：改需求走生成器整目录重生成，配 `--check` 位级一致守门。

**为什么冻结是必需的**：规则包一旦可手改，"引擎对不对"就永远无法与"数据对不对"分离——测试失败时无法判断是代码 bug 还是有人改了数据。冻结 + 位级一致守门把这两个问题彻底隔开。

确定性生成的三条纪律：禁 `stdlib random`、禁 `set` 迭代序、禁系统时钟；产物无时间戳；JSON 序列化固定（`sort_keys` + `ensure_ascii=False` + `indent=2` + LF 行尾）。

## 三、三态判定框架

### 3.1 状态定义

结论只有三态：`compliant`（符合）/ `noncompliant`（不符合）/ `not_provided`（未提供）。

此外两种**非结论**必须与三态可区分：

| 状态 | 语义 | 判据 |
|---|---|---|
| `skipped` | **不适用** | 只给"原文明确写了例外情形"的项 |
| `unknown` | **未观测** | "没看到"而非"缺失" |

### 3.2 三条硬纪律及其理由

**纪律一：无条件义务缺失 = 不符合。**

原文写"应当标示 X"（无条件义务）而缺 X，记 `noncompliant`。**绝不记成"不适用"**——那会把"没做"记成"不用做"，让合规结论虚高。这是合规/审计类工具**最容易被攻击的失分点**，比误报更严重：误报会被用户发现并纠正，假合规不会。

判别口诀：**"这项义务有没有前提条件？"** 原文是"应当 X"→ 缺 X 记不符合；原文自带"不适用情形"→ 才允许 `skipped`。

**纪律二：一条规则都不适用 → 维度"未评估"。**

`not_assessed` 绝不输出成 `compliant`。"没查出问题"与"没检查过"必须可区分——这是判定类工具的基本伦理。

**纪律三：零生效规则的维度不参与聚合。**

维度参与聚合的判据 = **该维度对这份输入有 ≥1 条生效规则**。不参与的维度记录 `dimension_excluded` + 原因码，报告保留区块并写明排除理由。

理由：把零生效维度塞进跨维度聚合，会把整体结论无谓拉成"未评估"（假性降级），或拿"尚未生效"的限值判违规（假性违规）。

### 3.3 义务类型分栏

法规条文里同一门槛可能挂性质完全不同的义务：

| `effect` | 语义 | 是否计入频次 |
|---|---|---|
| `obligation` | 无条件义务（"应当标示 X"） | **是**（频次只取这一栏） |
| `conditional` | 条件触发（"监管部门可以要求…"） | 否——监管裁量权不是处理者的无条件义务 |

混在一个布尔里输出，会把监管的裁量说成企业的法定义务（虚增义务面）。结论**分栏呈现**，报告分节不得合写。

## 四、双重门控

### 4.1 问题

一条规则常有两类独立可核对的要素：**数值本身**（限值是多少）与**条款号/原文位置**（在标准第几条）。

耦合成单一 `status` 的两个失败方向：

1. 条款号核不到 → 已核对数值也被无谓阻断（引擎无可判项）；
2. 只看数值 → "条款号没核对却看起来已核对"的风险。

### 4.2 解法

每条规则挂**两个独立状态**：

| 字段 | 语义 | 作用 |
|---|---|---|
| `status` | **数值**核对状态 | **唯一门控判定路径**的开关 |
| `clause_status` | **条款号**核对状态 | 只管可证性展示，**不阻断判定** |

两个状态都在产物与报告里**显式可见**（"未启用清单"打印 pending 条目）。

判别口诀：**"判定要素"与"可核证要素"是两回事，各自的核对状态各自显式呈现。**

### 4.3 门控按计算路径分作用域

`effective_ruleset(scope)` 的 `scope ∈ {label, nutrition, claim}`，各只校验自己引用的条目。

**不用"整包全 verified"当唯一门**——否则与某路径无关的 pending 会阻断整条路径。例如营养限值规则包里有几条待核对的条款号，不应阻断标示项检查。

## 五、数值口径一处定义（零政策字面量门禁）

限值数值**只存在于规则包**一处，判定、报告、基准全部引用它。配套门禁把全部规则包数值收编为**禁用 token**，扫描引擎/基准/CLI/GUI 源码，**含 docstring 与注释**。

### 5.1 门禁自己的输入也不许是代码字面量

token 从规则包**运行时实算**（`banned_numeric_tokens()`），不写死在扫描器里。理由：若把政策数值写进扫描器源码，扫描器本身就成了"第二份真相"，而且扫描器要过自己的扫描时会出现自噬。

### 5.2 豁免口径写死

- `abs(value) < 100` 的结构性常数（下标/计数/短文本长度）豁免；
- 豁免按**规则名 + 路径**绑定，不写成"这个文件全放过"；
- 词边界用 `(?<![0-9A-Za-z_.])…(?![0-9A-Za-z_.])`——避免把 `2200` 里的 `220` 当命中（子串误报是这类门禁最常见的失效方式）。

### 5.3 门禁广度：交付面扩张即扫描面扩张

门禁不区分"算数的代码"与"展示的文本"。新增任何交付形态（GUI、报告模板）都要先问：**这个文件里会出现政策数值形态的字符串吗？**

## 六、合成标签基准设计

### 6.1 为什么程序化自制

"没有标注数据"是这类项目的死结。解法：**随机生成输入 + 植入真值**，固定 seed 可复现，评测零成本重复。

### 6.2 确定性 RNG

用自研 **splitmix64**，不用 `stdlib random`——后者的序列在 CPython 各版本间**不承诺一致**，而基准必须跨机器、跨版本逐字节可复现。

### 6.3 真值语义（一次定清）

| 字段 | 语义 |
|---|---|
| `expected_overall` | 主期望（整体结论） |
| `expected_findings` | 逐规则期望结论 |
| `also_expect` | **同一注入隐含的其余结论** |
| `injected` | 植入了什么缺陷（人类可读，供审计） |

对账语义收成**单一实现源**（`observed_nonpass` / `compare_nonpass`），真值库测试与基准**共用**同一函数——否则会出现"基准说达标、测试说不过"的双口径漂移。

**非 pass = fail ∪ unknown**，`skipped` 排除在外（那是"不适用"不是"缺失"，纳入会制造假结论）。

### 6.4 四类植入

| 类 | 植入内容 | 期望检出 |
|---|---|---|
| 合规样例 | 全部强制项齐备 + 保证值达标 + 宣称有支撑 | 无非 pass |
| 缺项样例 | 逐项植入缺失 | 对应项不符合 |
| 越限样例 | 保证值低于对应档限值 | 对应指标不符合 |
| 宣称无支撑样例 | 宣称存在但缺其适用条件要求的信息 | 对应宣称不符合 |

**假品牌名白名单**：品牌名必须命中白名单，否则生成器 exit 1——禁止真实品牌入库为基准样例。

### 6.5 样本驱动 + 规则驱动两层

| 层 | 做法 | 证明什么 | 局限 |
|---|---|---|---|
| 样本驱动 | 真值库全量重算对账 | 引擎**在这些样本上**对 | 样本没覆盖的端点它证明不了 |
| **规则驱动** | 不读真值库，只从规则表推导切换端点，做 ±精度邻域断言 | 引擎在**所有有限端点上**对 | 需要能从规则表推导端点 |

判别口诀：**"这个基准的分母，是否依赖真值库恰好覆盖了某个端点？"** 依赖就是样本驱动，要补一条规则驱动的。

### 6.6 可证伪（探活）

**不配探活时"基准全绿"可能只是"基准什么都没查"。** 每套件配探活测试：注入缺陷 → 基准必须报未达标。

**探活的隐含前提 = 期望必须有独立来源。** 若期望值与引擎同源（都读现行规则包），注入缺陷时两边一起变，探活永远绿——那是装样子的永绿门。故期望锚定**冻结真值库**。

**注入方向随套件类型而反转**（M4 实测补上的一条）：

| 套件 | 驱动方式 | 什么样的注入能证伪它 | 什么样的注入**不能** |
|---|---|---|---|
| `boundary` | 规则驱动 | **引擎算错**（`Rule.compare` 恒真） | 改规则数值（真值从规则表推导，两边一起变） |
| `overall` / `detection` | 样本驱动 | **引擎聚合/判定算错**，或**真值库期望被篡改** | 改规则数值（期望锚定冻结真值，两边一起变） |

**M4 之前 `overall` 套件没有任何探活**——变异验证实测：把 `run_overall` 的比较改成恒真（`if True:`）、或把 `passed` 改成恒 `True`，
**231 项测试全绿**；对照组同样手法改 `run_boundary` 的 `passed` → **立刻 1 项失败**。
即"`overall` 的达标判定不可证伪"。M4 补齐两条注入方向（引擎聚合恒假 / 真值期望被篡改）+ 一条阳性对照。

**方法论：每次变异验证都要留一个已知有效的对照组。** 只看到"改坏了测试还绿"不能立刻下结论——
必须先确认变异手法本身在这个项目里是生效的（对照组变红），否则可能只是变异没生效。

> **本节的第二层教训（M4 最重要的一条）**：**"有测试"≠"测试有效"**。
> M4 本棒两次写出**假门**并靠变异验证当场发现：
> ① CI 覆盖门首版用**子串匹配**——把 `gen_cases.py --check` 整段注释掉仍绿；
> ② README 指标门首版用**全文件子串匹配**——把 `accuracy=1.0` 手改成 `0.9` 仍绿（别处还有别的 `1.0`）。
> 两者的共同形态是"判据验的是**文档排版**，不是事实"。
> 修法：判据落在**结构位置**——解析 workflow 的 `run` 步骤（注释不是步骤）、定位到"实测指标"小节后**在该行内**逐项核对。

### 6.7 空分母不冒充通过

误报对照零样本时 `hits(0) <= max(0)` 恒真、一致率恒 1.0——"没查"被读成"查了没问题"。

正解：空分母分支统一 `not_enabled=true` + notes 写明"该类用例未生成" + **exit 1**。

判别口诀：**每个"达标"分支先问"分母为 0 时它会怎样？"——恒真就是假门。**

### 6.8 门槛随 manifest 下发

验收门槛（`min_accuracy` / `max_false_positive` / `max_runtime_sec`）**随规则包 manifest 下发**，基准层**只读**；缺失即报配置错误（exit 2），**不得回落代码里的默认值**。

理由：门槛内联在引擎里就是"抄进代码的第二份真相"——调门槛要改代码，也易被误读为政策数值。

### 6.9 覆盖声明要"总数/采样数"双数

`manifest.json` 的 `coverage` 逐维度登记 **"规则包总数 / 已核对数 / 真值库采样数 / 采样清单"** 并声明"抽样覆盖、非逐因素穷举"。

判别口诀：**"这个覆盖声明里，分母（总数）和分子（采样数）都写出来了吗？"** 只写分子就是假覆盖。

**但"写出分子"还不够——分子本身的口径也要写死**（M4 实测的第二层坑）。
真值库的 `expected_findings` **只记非 pass 的显式期望**，合规类用例是 `{}`——但它同样逐条判了全部生效规则。于是"采样数"有两个候选口径：

| 口径 | 定义 | 本项目实测值 | 问题 |
|---|---|---|---|
| **显式期望**（采用） | 真值库为该规则**写下明确非 pass 期望**的规则数 | label 3 / nutrition 4 / claim 3 | 携带真实信息（覆盖确实非穷举） |
| 被用例触达 | 判定过程中产生过 finding 的生效规则数 | label 8 / nutrition 30 / claim 5 | **恒等于生效规则总数**，永远 100%，不携带信息 |

选后者就会得到"**又一个假台账**"：数字漂亮、且与"抽样覆盖非穷举"的声明自相矛盾。
故口径写死在 `COVERAGE_NOTE` 里，并配非空转守门（`test_coverage_sampled_count_is_not_vacuous` 断言采样数**严格小于**生效规则数——哪天退化成"触达"就变红）。

### 6.10 冻结真值库必须"入仓 + 有守门 + 有调用方"（K29，M4 新增）

"期望锚定冻结真值库"这句话要成立，三件事缺一不可：

| 要素 | 缺失时的失效形态 |
|---|---|
| **入库件存在** | `data/benchmark/cases.json` 不存在 → 无物可锚 |
| **常驻位级守门** | 无 `gen_cases.py --check` → 入库件被手改无人知 |
| **真有调用方** | 基准每次现场重算 → **入库件是个没人读的文件**（M4 实测的旧形态：`load_cases()` 全仓零调用） |

M4 之前的实测事实：三条里**第一条与第三条都不成立**——生成器已实现、`check_cases_frozen()` 却只在测试里被调，
**`src/` 与 `tools/` 里零调用**。故落盘 `cases.json` 之后基准**仍然不会用它**，"冻结"只是名义上的。

**处置**：`runner._sample_cases()` 改为**入库件优先**（并把来源写进 metrics：`truth_source=frozen|regenerated`）；
入库件与生成器输出不一致 → `BenchConfigError`（exit 2），**不静默重算**——真值漂移必须响。
同时把 `cases.json` 收进 `DATA_WHITELIST`：**发行态也得有它**，否则发行态的基准只能回落现场重算
（源码态 `frozen`、发行态 `regenerated` —— 源码态绿而发行态名不副实）。

## 七、溯源完整性

交付物里每条结论/数值都必须能追到规则条目。**导出前断言**："溯源表行数 == 明细行数"且"每条引用 id 可解析"，不满足即**报错拒导**。

理由：核证/审计类交付物里，**"半溯源"比"无溯源"更危险**——读者以为已可核证。

配套：**"未启用"的章节要显式写出**（"本次导出未启用 X"），不留空——"没查"与"查了没问题"是两种截然不同的结论，留空会被误读成后者。

## 八、报告双轨与单一渲染源

人读（Markdown）+ 机读（CSV）双轨。**两种格式都消费同一个 `report_sections()` 返回的结构化章节**——于是"两格式内容一致"不再是"导出后肉眼比对"，而是**结构上不可能不一致**（改一处两者同变）。

四条硬约束：

| 约束 | 落地 |
|---|---|
| 溯源完整性 | 导出前断言，不满足拒导 |
| 无外链 | 禁活动链接形态（Markdown 链接/HTML href/src/OOXML External）；**纯文本 URL 允许**——参数来源块要让读者不开仓库也能核证 |
| 逐字节可复现 | 自写最小 writer（不引第三方，避免 ZIP 元数据/文档属性时间戳漂移）；产物无时间戳 |
| "未启用"显式写出 | 章节不留空 |

**报告必含四块**：输入事实 / **参数来源块**（发布机关 + 文号 + 条款 + URL + 抓取日期）/ 逐项判定过程（直接渲染引擎留痕，报告层**不重算**）/ 适用依据 + 免责声明。

判别口诀：**"把报告单独发给一个没有仓库的人，他能看出数据出处吗？"**

## 九、分层与静态门禁

### 9.1 分层

判定逻辑**只有一份实现**，位于编排层（`pflc.pipeline`）之下；CLI 与 GUI 都是"取数 + 渲染"的薄壳。

判别口诀：**"同一个业务判断在项目里有几处实现？"多于一处就是上收没做完。**

### 9.2 GUI 零判定逻辑靠 AST 静态门禁（三条齐上）

| 断言 | 抓什么 |
|---|---|
| 不 import 规则层/引擎内部模块 | 通道 |
| **无算术运算 `BinOp`** | 界面里直接算（`size * 1.5`） |
| **无政策数值字面量** | 界面里内联政策值 |

**只守 import 面会漏掉后两种绕过**。判别口诀：**"层里没有判定逻辑"要能被机器证明，而"不 import 引擎"只证明了通道，没证明内容。**

**豁免口径必须写死**，否则门禁刷屏而被人关掉。本项目的豁免：
- 任一操作数是**字符串字面量** → 格式化/路径拼接，不算算术；
- **路径拼接**（`Path / str`）→ 按 path-like 名字传播判定，不是除法；
- 赋值给**布局命名**（`*_WIDTH` / `*_HEIGHT` / `*_SIZE`）的数值 → 窗口尺寸不是政策数值；豁免绑定**命名**而非整个文件，界面里写 `LIMIT = 150` 仍会被抓。

### 9.3 门禁必须做变异验证

**每条门禁都要故意弄坏被测行为一次，确认它变红**。弄坏后仍绿 = 假门。

尤其：`assert "xxx" in source` 这类字面断言证明不了函数被调用。本项目的行为等价测试用**三方对账**（CLI stdout 结论 == 直接调 pipeline 字段 == 报告章节结论），而非字面声明。

**实测收益**：GUI 门禁当场抓出一个真 bug——三个结果页签复用了同一个 `QPlainTextEdit`，而 Qt 控件只能有一个父级，重新父化导致页签数从 6 塌成 4。这是"靠自觉守不住、靠静态检查才守得住"的实例。

### 10.4 M1 数据获取方法（两处"看似不可得"实际都拿到了）

## 十一、桌面交付与冻结态验收（M5）

### 11.1 为什么"发行态"需要独立的验收通路

M5 的难点不在写界面（`gui/app.py` 自 M0 就在），而在**发行态名不副实**——
本项目已有一整套准备（构建后三断言、冻结态自检、中立目录验收），M5 的任务是让它们
**真的跑起来并真的能判出坏产物**。

两类失效只能靠"真构建 + 真跑 exe"暴露，**本地源码态测试全都看不到**：

1. **构建配置对 ≠ 产物对**：PyInstaller 构建成功、退出码 0，而 exe 一启动就崩；
2. **判据深度隐式**：写门的时候按当时的目录布局写死深度，换布局后门**永久恒绿**。

### 11.2 M5 实测修掉的 4 个真缺陷

| # | 缺陷 | 为什么源码态看不见 | 修法 |
|---|---|---|---|
| 1 🔴 | **spec 入口点打断包语义**：Analysis 直接指向 `src/pflc/cli.py`，PyInstaller 以**顶层脚本**方式运行它 → `from . import pipeline` 无父包可挂 → 冻结后 `ImportError: attempted relative import with no known parent package` | 源码态跑的是 `python -m pflc.cli`（有包上下文），执行路径完全不同 | 新增 `tools/entry_cli.py` / `entry_gui.py`：只做"绝对导入进包内 main"；配 spec 入口门（AST 解析 Analysis 脚本 + 断言入口文件顶层无相对导入） |
| 2 🔴 | **禁区扫描判据恒绿**：`assert_no_forbidden` 只匹配 `len(rel.parts) <= 2`；PyInstaller 6.x 把数据放 `_internal/data/`，禁区目录在三级深 → 判据**永远看不到**它 | 判据的深度假设是隐式的，没有真实 6.x 布局就没有反例 | 扫描面改为"负载根（`_internal/` 与平铺两种布局）下的 `data/**` 任意深度"；配 6.x 真实树 + 干净树**两组对照** |
| 3 🟡 | **CLI 包白送 87 MB 且降级提示成死代码**：两个 Analysis 共用同一份 hiddenimports，PySide6 进了 CLI 包 | 体积不是功能断言；两台 exe 在源码态都"能跑" | 拆 `_BENCH_HIDDEN` / `_GUI_HIDDEN`；CLI 侧 `excludes` 加 PySide6/shiboken6。实测 **112 MB → 17 MB**；冻结态 `gui` 实测 exit 3 |
| 4 🟡 | **降级提示未按形态分流**：对冻结态用户也提示 `pip install -e ".[gui]"`——**冻结态用户没有 pip** | 原测试只断言退出码，不看提示文本 | `cmd_gui` 按 `is_frozen()` 分流；测试加**双向**断言（源码态含 pip / 冻结态**不含** pip 且含"桌面版"） |

**另做实一道"声称已有其实没有"的门**：`packaging.py` 的 docstring 声称
"三处守门（spec 文本、构建后扫描、白名单外检测）"，但 spec 文本那道门**并不存在**。
本棒补上 `test_spec_does_not_hand_write_data_paths`——**docstring 声称的门与被声称的门是同一条时，
要确认它真的存在**。

### 11.3 验收由构建事实驱动，而非由脚本猜

`tools/verify_frozen.py` 的验收输入是构建期写下的 `_datas_report.json`：

```json
{ "data_whitelist": ["rules","benchmark","samples"],
  "datas": [{"src_rel":"data/rules","dest":"data/rules"}, ...],
  "sha256": {"data/rules/manifest.json":"2fa0aafa…", ...},
  "kind": "cli", "exe_names": ["pflc-cli"] }
```

它带来三件事：

* **"spec 没手写数据路径"可核证**：报告里的清单与当前白名单对账，多打少打都报错
  （这一条 sha256 对账抓不到——对账基准取自仓库现算清单，手加路径照样一致）；
* **验收知道该验哪个 exe**：两个发行树形态不同（CLI 树没有 GUI、GUI 树没有 `check` 子命令），
  由 `kind` / `exe_names` 声明，而不是让脚本猜目录名；
* **报告缺失即报错**：空报告与合规报告不能长得一样——否则又是一道恒绿门。

### 11.4 又一道假门："子串判据"

新增的 CI 门首版判据写：

```python
assert "--dist dist/pflc" in joined          # ❌
```

而 `"dist/pflc"` 是 `"dist/pflc-cli-dist"` 的**子串**——把 GUI 那步整段注释掉后，
判据照样命中而保持绿。变异验证当场抓出，改成正则**锚定完整参数**后才真红：

```python
re.search(r"--dist\s+dist/pflc\s+--selftest", joined)   # ✅
```

**这已是本项目第三次踩到"子串判据"**（M4 两次 + M5 一次）。
结论固化成一条写法纪律：**写判据时默认自问"有没有更长的字符串把它包含进去"**。

### 11.5 审计扫不到的地方：演示素材里的本机路径

"关于"页会把**数据目录的绝对路径**打在界面上（对真实用户而言这是有用信息）。
但生成演示素材时，**本机工作根路径会被烤进 PNG**——而脱敏审计按扩展名把 PNG
当二进制跳过（`EXCLUDE_SUFFIXES`），**完全看不到它**。

处置：在**产素材那一步**替换成中性占位符 `<数据目录>` + 硬断言，
而不是等事后审计（它根本看不到）。断言判据刻意落在"**盘符路径起始位置**"
（`(?<![\w])[A-Za-z]:[\/]`）——**不能拿 `":/"` 当判据**，因为参数来源块里
`https://` 很多，会大面积误报（本生成器第一次加断言就误报了）。

这与 M4 的 `--tracked` 坑是同一族：**绿 ≠ 验过了**——
审计没报，可能只是它没扫到。

## 十二、发布与可核证性（M6）

发布的难点不在"把产物传上去"，而在**让陌生人能独立核证**：他拿到的字节是不是我们验过的？
包里的数据是不是仓库里那一份？"确定性打包"这句话到底对什么成立？本章把 M6 的做法与
**踩到的两个概念混淆**都记下来。

### 12.1 两棵树各打一个 zip（而不是一个大包）

发行产物是**两棵独立的树**（见 §十一）：桌面包内嵌 PySide6，CLI 包**特意不含**
（它对 `gui` 子命令走 exit 3 分流）。合成一个大包会让那句降级提示变成死代码，
并白送约 87 MB。故发布物是**两个附件**，让"下哪个"显式化。

### 12.2 "确定"是对什么确定——一个必须问清的前提

M6 给打包写了确定性判据（`ZIP_STORED` + 条目字典序 + 固定时间戳 + 固定外部属性），
并配了"两次独立打包 sha256 必须一致"的常驻门。但**首次上 CI 就被这条判据打回来了**：

我们原本还要求"**在别处重建一次**，zip 哈希必须等于留档"。这在 CI 上**永远不可能成立**——
因为 **PyInstaller 产出的树本身不是逐字节可复现的**：exe 里含构建期 PE 时间戳等信息，
实测**同一台机器两次构建**，`pflc-cli.exe` 的 sha256 就不同（`813da5e1…` / `9a355663…`）。

**这是两个不同的命题，混在一起就会写出做不到的判据**：

| 命题 | 成立吗 | 判据怎么落 |
|---|---|---|
| **打包确定性**：同一棵树打两次，zip 逐字节一致 | ✅ 成立 | 常驻门：两次 `build_zip` 比对 sha256 |
| **构建可复现性**：跨机/跨次重建，产物逐字节一致 | ❌ **不成立**（PyInstaller 含构建期信息） | 不该要求；改验**结构口径** |

修法：留档增记**树 sha256**（说清"这个 zip 从哪棵树打的"），对账分两种情形——
**树一致**则 zip 哈希与文件数逐条强对账；**树不一致**则只验结构口径
（附件名齐备 / `ZIP_STORED` / 条目排序 / 回读保真）。

**顺带定位了一处环境差异**：CI 产物比本机多 43 个文件，逐文件清单比对后确认
**全是 Universal CRT**（`ucrtbase.dll` + 42 个 `api-ms-win-*.dll`）——本机 UCRT 在
`System32` 故 PyInstaller 视其为系统库不收，runner 上则可解析位置不同被收进包。
**清单打进 stdout** 让这类差异可观测，而不是靠猜。

### 12.3 产物本体扫描：审计盲区的独立通路

脱敏审计 `audit_desensitize.py` 按扩展名把二进制当不存在（`EXCLUDE_SUFFIXES` 含
`.exe`/`.dll`/`.pyd`），而 `dist/` 又在 `.gitignore` 内（`--tracked` 按 `git ls-files`
枚举）——**两条路都到不了发行包**。但发行包恰恰是**要发给陌生人的东西**，
带本机路径的后果最重。故 M6 另立一条通路扫**产物本体**。

**判据形态**：按**字面量**匹配，且 ASCII 与 **UTF-16LE** 两种编码各编一遍。
不用文本正则的原因：exe/dll 里既有窄字符串也有宽字符串（UTF-16 每字符夹 NUL），
把字节当文本解码会漏宽串；而"去掉 NUL 再匹配"会把本就相邻的字符**拼成假阳性**。

**判据源单一**：文本通路的 `scan_criteria()` 与产物通路的 `sensitive_literals()`
同源（都吃 `compute_tokens()` 的输出）。本项目已两次踩中"同一口径各写一份 → 修一边漏另一边"，
故这里刻意不给第二条通路留独立的判据表。

**分级语义**：只 **HARD 阻断**（本机用户名签名 / 提交邮箱 / 密钥 / 身份证 / 手机号）；
`repo_path_segment` 一类 REVIEW 只报不阻断——它的取值**随构建环境变化**
（CI runner 上是 `home`/`runner`/`work`），若也阻断，同一仓库在不同 runner 上会
**时红时绿**（环境决定的假红）。

### 12.4 变异验证抓出的一处自造假门

新加的"边界环视"阴性对照，样本用了 Qt 二进制里真实存在的 `ASUSTek COMPUTER INC`。
但它**根本不含**针 `Users\<用户名>`——判据靠**前缀**就把它排除了，
**边界环视整段空转**（把环视删掉测试仍绿）。

改用 `Users\<user>Other`（以用户名为前缀的**更长目录名**）才真的探活。
**教训**：阴性对照样本必须**真的命中判据的待测部分**，否则它证明的是别的东西。

同族的一个更基础的坑：变异脚本的对照组一开始写的是"重命名测试函数"——
那只是把它**移出收集集**（`44 passed` vs `45 passed`，**exit 0**），不产生失败，
是**无效对照**。对照组必须改**被测行为**。

### 12.5 转公开三清：历史重写的两个实施细节

历史里的本机用户名路径与提交元数据的私人邮箱，在切公开 visibility 的那一刻即永久公开。
清它需要**改写 git 历史**（不可逆、破坏性），故：

* **时机**：重写时仓库**尚无远端** → 旧副本无人持有 → 无强推面；先做 `git bundle` 全量备份，
  再在一次性 clone 上**演练**通过才动真仓库；
* **邮箱改写走 `--email-callback` 而非 `.mailmap`**：mailmap 每行都要写成
  `<新邮箱> <旧邮箱>`——把私人邮箱**原样写进一个仓库文件**；那文件要么入仓（自曝，
  等于没脱敏），要么留工作区（下一个人 `git add -A` 就带上）。callback 的目标邮箱算在
  `.gitignore` 内的临时脚本里，零残留。

重写后全历史 **HARD 3→0**；`--tracked` 与 `--messages` 保持 0。

### 12.6 首次上 CI 不可替代

M6 首跑 **7 个 job / 4 绿 3 红**，三个红**全是"本机绿、CI 红"一族**：
runner 的用户名/路径形态触发了另一条判据的合法命中、构建环境差异让留档对账不可能成立、
判据在不同环境下的稳定性（REVIEW 级阻断会导致时红时绿）。

**这三个都不是本机多跑几遍能发现的。** 故发布流程固定为：
**先建 private 仓 → push → 等 CI 首跑绿 → 再打 Release / 切 public**，
让公众看到的是绿的，而不是把红的 run 留在公开历史里。
